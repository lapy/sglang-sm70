## Deployment status (4x V100, 2026-11-10)

The stack **boots and serves** `Qwen3.8-Flash-Next-NVFP4` (TP4): 128 GB loaded at 19.89 GB/rank,
target-verify and draft-decode CUDA graphs captured, QSA kernels JIT-compiled, `/health` 200,
**84 tok/s decode** (`/generate`, 128 tokens, ignore_eos).

Correctness is not there yet: generations are degenerate (prompt echo, then zeros). Everything
environmental is fixed and every opt-in SM70 kernel has been ruled out — see
[issue #14](https://github.com/lapy/sglang-sm70/issues/14). The remaining suspect is the merge of
the SM70 port into upstream's newer Qwen4 forward path (`srt/models/qwen4_exp.py`,
`srt/layers/hyperconnection.py`), so the next step is a hunk-by-hunk comparison against
`sglang-sxm2`, which serves this model correctly on the same hardware.

Environment facts that cost the most time (all now in the install section above and in #12):

- `sglang-kernel` must be the torch-matching build; source builds with
  `-DSGL_KERNEL_V100_ONLY=ON` need the three build fixes from #12.
- No `nvidia-nccl-cu13` in the venv (it shadows torch's cu12 NCCL: "named symbol not found").
- `marlin_v100` needs `MARLIN_V100_SKIP_BF16_COMPAT=1` under CUDA 12.6.
- `--linear-attn-decode-backend tilelang`: Triton lowers `tanh` to PTX `tanh.approx`, sm_75+.
- FlashInfer must be the pinned revision **with** `patches/flashinfer-sm70.patch`, and the JIT
  sampling call must match its `DeviceSamplingFromProb` signature (7 args + `DETERMINISTIC`).
- PLE embedding offload is mandatory on 4x32 GB; on-device OOMs.

Serve path validated end to end on `Qwen3.8-Flash-Next-NVFP4`, TP4, 4x V100-SXM2-32GB:

| streaming | works |
| 2k-context question | answers correctly |
| throughput | 75 tok/s at 128 tokens with MTP (54 tok/s target-only) |

The earlier degenerate output (prompt echo) was a **missing dense marlin_v100 repack**: the loader
globs `_sm70_marlin_v100_dense*.so`, found nothing, and fell back to SGLang's in-tree repack, an
intentional zero-output stub below sm_80. Fixed in #15 (install the two extensions under the names
the loaders glob, verify through the loader, fail loudly when absent) with the write-up in closed
- #14.

Install notes that matter: `pip install -r requirements.txt` (torch 2.9.1+cu128), the V100
`sglang-kernel` wheel, `scripts/setup_v100_marlin.sh` for both marlin artifacts, FlashInfer at the
pinned revision with `patches/flashinfer-sm70.patch`, no `nvidia-nccl-cu13` in the venv, and PLE
embedding offload left on (it OOMs on 4x32 GB otherwise).
## Clean-tree verification (2026-11-11)

Re-verified from a fresh extraction of `sm70/stack` (no hand patches, JIT cache rebuilt), after
merging #12 (runtime fixes), #15 (dense marlin repack + fail-loud loader), #16 (import guards),
#18 (NVFP4 reference test green) and #19 (FlashInfer sampling signature):

- both marlin extensions reported at startup
- chat + reasoning -> `4` for "2 + 2"; tool call -> `get_weather {"city":"Dublin"}`, `finish_reason: tool_calls`
- streaming works; 2k-context question answered
- reference prompts: `The capital of Japan?` -> ` Tokyo`, `7 * 6 =` -> `42`, haiku and translation prompts answered
- **73.7 tok/s** at 128 tokens with MTP on 4x V100

Remaining known gap: none for Qwen3.8-Flash-Next-NVFP4. Two worth recording:

- `_sm70_marlin_v100_dense.abi3.so` and `_sm70_marlin_v100_moe.abi3.so` must both be installed under
  those exact names; the loader now raises instead of silently using the zero-output stub (#15/#16).
- the FlashInfer pin (`c3c40a7b` + `patches/flashinfer-sm70.patch`) is required, and the sampling
  kernel matches its `DeviceSamplingFromProb` signature (#19).
